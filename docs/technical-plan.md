# LeoAgent 开源技术方案

方案版本：2026-10-20。本文是 LeoAgent 的产品和工程基线；代码现状、测试证据和未完成项分别见[项目架构](architecture.md)与[实施记录](implementation-status.md)。

## 1. 产品定位

LeoAgent 是一个**自托管的手机 Agent 控制器**：

- 电脑端部署在用户自己的电脑上，长期在线，负责启动和管理本机编程 Agent。
- 手机端通过 HTTPS 操作电脑端，提交任务、查看输出、处理审批和回答问题。
- Agent 的模型登录和凭据仍由用户在电脑上配置；LeoAgent 不托管模型密钥，也不提供项目自建云中继。
- 电脑必须在线并保持可用。远程开机、休眠唤醒和电脑硬件管理不属于核心范围。

这里的协议名称是 **ACP（Agent Client Protocol）**，不是 ACPI。手机不直接连接 ACP；电脑端把 ACP 事件转换为 LeoAgent 的稳定 HTTP/SSE 模型。

开源首版的目标不是做一个完整的云端 Agent 平台，而是把“手机 → 用户电脑 → 本机 Agent”这一条链路做得可靠、可审计、可自行部署。

## 2. 首版必须守住的四个不变量

1. **电脑端是事实来源。** 手机只保存连接凭据、操作回执和显示缓存；任务状态、审批有效性、事件序号以电脑端 SQLite 为准。
2. **写操作可以重试，但不能被 LeoAgent 重复接受。** 任务、审批、回答、取消和未知核对都必须带操作 ID 与请求指纹。
3. **不确定就显示不确定。** 服务重启、管道断开或取消超时后，若无法证明结果，进入 `unknown` 或 `interrupted`，不自动重发，也不伪装成功。
4. **核心链路不依赖云服务。** 网络入口由用户自行提供；云推送、Relay、多主机调度和端到端加密都是后续可选组件。

这四条比具体 UI、某个 Agent 或某一种隧道更重要。新增功能必须先说明它如何保持这些不变量。

## 3. 总体架构

```text
┌──────────────────────────────────────────────────────────┐
│ Android 客户端                                           │
│ UI / 本地通知 / Keystore 凭据 / 操作回执 / 事件游标       │
└───────────────────────┬──────────────────────────────────┘
                        │ HTTPS JSON 命令
                        │ SSE 事件流 + HTTP 补取
                        ▼
┌──────────────────────────────────────────────────────────┐
│ 用户电脑：leoagent-server（单实例 Rust 服务）             │
│                                                          │
│ 入口层：认证、配对、API v1、SSE、限流、诊断               │
│ 控制层：项目/会话/任务/交互状态机、幂等回执、事件游标       │
│ 执行层：Agent 适配器、ACP/stdio、进程组、取消与重启对账    │
│ 存储层：SQLite WAL、迁移、备份、恢复、设备授权            │
│ 辅助层：文件、Git diff、截图、STT、APK 更新（可选）        │
└───────────────────────┬──────────────────────────────────┘
                        │ ACP / stdio JSON-RPC
                        ▼
                 本机 Agent 进程
```

外部连接只负责把手机请求送到电脑服务。Cloudflare Tunnel、Tailscale、Caddy 或局域网均可使用，但都不能替代 LeoAgent 的设备认证、任务回执和状态判断。

### 3.1 四个逻辑平面

| 平面 | 负责什么 | 首版要求 |
|---|---|---|
| 客户端平面 | 展示状态、发起操作、断线恢复 | 原生 Android；手机重启后从快照和回执恢复 |
| 控制平面 | API、认证、任务状态、事件、回执 | Rust/Axum/Tokio 单进程；所有写操作落库后才返回接受 |
| 执行平面 | 启动 Agent、发送 ACP、处理输出和退出 | ACP 为主；子进程按服务持有的身份清理 |
| 辅助平面 | 文件、截图、语音、更新 | 可关闭、可单独验证，不阻塞核心对话链路 |

当前代码可以继续放在一个 Rust 二进制中；“四个平面”是职责边界，不要求现在拆成四个进程或服务。

### 3.2 技术取舍

| 部分 | 选择 | 为什么适合当前目标 |
|---|---|---|
| 电脑端 | 保留 Rust + Axum + Tokio 单服务 | 延续进程管理和 API 实现，减少安装与运维组件 |
| 存储 | 保留 SQLite WAL | 单机事务能同时完成回执、任务占用和事件写入，无需 Redis 或消息队列 |
| 手机端 | 保留 Kotlin + View，渐进拆分 | 现有界面可以复用；先集中完成断线恢复，不同时更换 UI 框架 |
| 手机通信 | HTTP JSON + SSE + HTTP 补取 | 命令和事件职责分明；无须为统一形式切换为 WebSocket |
| Agent 接入 | ACP，按能力协商 | 优先打通一个参考 Agent，再扩展版本和适配器 |
| 电脑管理 | CLI + macOS 用户级 launchd | 先完善安装、诊断、配对；托盘后续仅作为管理入口 |
| 网络入口 | 首条教程以 Tailscale 私网 HTTPS 为目标，隧道/反代作为替代 | 复用用户已有连接能力，不运营自己的中继 |

上述网络入口是部署选择，不表示已完成新用户从零安装验收。服务器默认仍绑定 `127.0.0.1`，不把 HTTP 端口直接暴露公网。也不默认要求 Docker：本机 Agent 登录、用户目录和桌面截图都需要额外映射，容器应作为后续可选执行隔离方式。

## 4. 组件设计

### 4.1 电脑端服务

电脑端是系统的状态机和权限边界，负责：

- 一次性配对、逐设备凭据、撤销和本机管理 CLI；
- 项目、会话、任务、审批、提问、取消和未知核对；
- Agent 进程启动、复用、超时、取消、退出检测和进程组清理；
- ACP 能力协商以及供应商事件到统一事件模型的转换；
- SQLite 事件日志、快照、增量补取、备份、恢复和数据库迁移；
- 文件浏览、Git diff、截图、可选 STT 和 APK 更新接口。

路由层不应直接拼接 Agent 原始 JSON。业务层先把供应商消息转换为稳定的 `task`、`interaction`、`event` 和 `operation_receipt`，再交给存储和手机端。

### 4.2 手机端

手机端是可随时断开、重启和重复提交的远程控制器：

- 只保存电脑连接信息和设备凭据，不保存模型密钥；
- 提交操作前保存 `operation_id` 与原始参数，响应丢失时查询原回执；
- 前台优先 SSE，失败时按游标 HTTP 补取；收到 `reset` 或数据代数变化时重新读取快照；
- 将“连接中断”“任务运行中”“结果未知”“交互已失效”分别展示；
- 后台通知按尽力而为处理，不能把 Android 后台轮询描述成系统级远程推送。

当前 UI 仍集中在 `CodexPane.kt`，后续按 `UI → ViewModel → Repository → API/EventStream` 渐进拆分；不为了目录漂亮而先做大规模重写。

### 4.3 Agent 适配层

内部适配器需要表达以下能力：

```text
probe()                         -> 可用性、版本、能力
open_session(identity)          -> 运行句柄
send_prompt(handle, content)
answer_permission(handle, id, decision)
answer_question(handle, id, answer)
cancel(handle)
close(handle)
```

ACP 是默认适配器。每个 Agent 记录启动命令、探测方式、支持的平台和版本、会话恢复方式、审批/提问能力以及已验证日期。能力声明只允许收窄客户端行为；没有实测的能力不能写成“支持”。

服务重启后不承诺重新接管旧 stdio 管道。若 Agent 支持显式历史加载，用户可以发起新的接续任务；恢复失败必须显示上下文未恢复，而不是静默创建同名新会话。

### 4.4 可选能力

截图、STT、桌面 IPC、APK 更新和文件预览都属于辅助能力：

- 未启用时不影响任务、审批、事件和配对；
- 有独立权限、超时和错误反馈；
- 不把桌面 IPC 或某个 macOS 工具作为核心执行前提；
- 不把项目目录的路径检查描述成操作系统沙箱，Agent 仍以本机用户权限运行。

## 5. 领域模型和状态语义

### 5.1 核心对象

| 对象 | 作用 |
|---|---|
| `device` | 一台手机及其可撤销凭据 |
| `project` | 电脑上的工作目录和项目元数据 |
| `session` | Agent 对话身份，可跨任务延续 |
| `task` | 一次用户提交及其最终状态 |
| `interaction` | 一次审批或提问，带有效期和处理结果 |
| `event` | 可补取的有序事实记录 |
| `operation_receipt` | 写操作的持久回执和请求指纹 |
| `runtime_instance` | 服务拥有的 Agent 子进程身份和退出证据 |

### 5.2 任务状态

```text
queued → running → succeeded / failed
          ├── waiting_approval / waiting_input → running
          └── cancelling → cancelled / unknown

服务重启：active → recovering → confirmed_state / unknown
```

- `queued` 表示已持久化、尚未派发；服务在这个边界崩溃可明确失败。
- `running` 表示可能已经向 Agent 派发；没有结束证据时不能在重启后自动重发。
- `waiting_approval` 和 `waiting_input` 由有效 `interaction` 集合决定；交互失效后按钮必须禁用。
- `cancelling` 只有在确认 Agent 停止后才能进入 `cancelled`；超时进入 `unknown`。
- `succeeded` 只表示 Agent 回合正常结束，不表示代码已经通过测试。
- `interrupted` 表示人工确认过中断；它也不等于没有产生副作用。

首版并发约束：同一会话一个活动任务；同一项目默认一个会修改工作目录的任务；全局活动任务有上限。项目忙时返回可解释的 `project_busy`，不在后台隐式排队并改写用户目录。

### 5.3 事件与快照

事件使用同一数据库内持续递增的全局序号。当前[事件封装](event.schema.json)以 `seq/type/data` 为基本字段，任务关联可以为空；会话由查询路径限定，`data_epoch` 和 `server_generation` 由快照及响应外层携带。后续扩展必须兼容已有消费者，不把目标字段误写成当前每条事件的必填字段。快照与最大序号在同一读事务内取得：

1. 读取任务状态、有效交互、最近事件和游标 `S`；
2. 客户端以 `seq > S` 补取后续事件；
3. 重复事件按序号去重，只推进到实际应用的最大序号；
4. 游标代数变化或服务要求 `reset` 时，重新读取快照。

内存广播只负责唤醒 SSE；SQLite 是断线补取的依据。慢客户端得到有界缓冲或 reset，服务不能无限堆积内存。

状态变更与对应事件在同一个写事务提交。事件序号在不同会话之间可能跳跃，客户端不能据此认定本会话丢包。普通服务重启保留 `server_id` 与 `data_epoch`，仅更新 `server_generation`；恢复备份另行轮换 `data_epoch`，防止旧游标和恢复点之后的积压操作被误用。

## 6. API 和网络协议

### 6.1 版本化接口

新客户端使用 `/api/v1`，旧 `/api` 只作为过渡兼容层，并且必须复用同一业务入口。核心接口：

```text
GET  /api/v1/health
GET  /api/v1/projects
GET  /api/v1/sessions
POST /api/v1/sessions
POST /api/v1/sessions/:id/tasks
GET  /api/v1/sessions/:id/snapshot
GET  /api/v1/sessions/:id/events?after=...
GET  /api/v1/sessions/:id/stream?after=...
POST /api/v1/interactions/:id/respond
POST /api/v1/tasks/:id/cancel
POST /api/v1/tasks/:id/resolve
GET  /api/v1/operations/:id
```

响应包含稳定的 `code`、`message` 和 `request_id`。`202 Accepted` 只代表任务和回执已经持久化，不代表 Agent 已经完成。OpenAPI 和事件 JSON Schema 作为仓库中的可审查契约；CI 应用真实 HTTP 响应验证它们。

### 6.2 写操作与幂等

客户端写请求携带操作 ID 和原数据代数；服务器从认证结果取得调用方，并计算请求指纹后持久化：

```text
caller_id            由设备凭据导出，不信客户端自报身份
operation_id         客户端生成并在发送前保存
request_fingerprint  服务端根据规范化请求计算
data_epoch           客户端绑定提交时的电脑数据代数
```

处理规则：

- 相同调用方、相同操作 ID 和参数：返回原回执；
- 相同操作 ID 但参数不同：返回冲突；
- 事务中同时检查权限、会话/项目互斥、任务和回执；提交成功后才唤醒执行器；
- 响应丢失时，客户端查询原操作 ID，不生成新任务；
- 只有已保存的“被拒绝”回执才能让手机清理本地待操作；一次 HTTP 401/404 不能证明早先操作没有被接受。

这保证 LeoAgent 不会因网络重试重复接受同一控制操作，但不承诺 Agent 内部命令或文件副作用具有 exactly-once 语义。

去重键和请求指纹不随普通对话删除而清理。未来如需回执过期，必须同时引入服务端可验证的请求有效期；仅删除旧记录会使晚到请求被再次接受。所有待确认写操作绑定原 `data_epoch`，换库后不能拿新的代数自动重发旧操作。

### 6.3 SSE 和补取

SSE 是实时显示通道，HTTP 补取是必需后备。流中携带服务代数、数据代数、游标、事件和 reset 信号。代理必须允许 SSE、关闭响应缓冲，并使用 HTTPS；服务默认只监听 localhost。

## 7. 持久化、重启和运维

SQLite 采用 WAL 和版本化迁移。核心表包括 `projects`、`sessions`、`events`、`tasks`、`interactions`、`operation_receipts`、`runtime_instances`、`devices`、`pairings`、`deferred_prompts` 和 `schema_migrations`。

服务启动时：

1. 获取数据目录单实例锁；
2. 在事务中执行已知迁移；未来版本直接拒绝启动；
3. 读取活动任务和运行实例，按 PID、进程启动时间、服务代数等证据对账；
4. 未派发任务标记失败，已派发但无终态记录的任务标记 `unknown`；
5. 旧审批和提问作废，不向新进程重放；
6. 刷新事件并开始接收新请求。

`doctor` 是只读检查，不启动 Agent、不读取模型凭据。`backup` 使用 SQLite 一致性备份；`restore` 必须停服、预校验和轮换 `data_epoch`，并撤销恢复点之前的设备凭据。恢复数据库不能回滚项目文件副作用，因此任务结果需要人工对账。

优雅退出先停止接单、关闭订阅、清理自己持有的 Agent 进程组，再刷事件和对账。不能根据磁盘里保存的旧 PID 直接杀进程，也不能保证清理已经主动脱离进程组的后代。

异步提问的派生回答保存在 `deferred_prompts`，按原交互 ID 去重；父任务成功后才接纳后续任务，父任务失败或结果未知时阻塞。它不是通用用户任务队列，不改变“项目忙时返回忙提示”的策略。

首版只承诺手机断线后任务继续。若未来要求**电脑服务重启后原回合仍可接管**，需要另设本地执行器和可重连通道，承担协议、升级和进程所有权成本；单纯增加数据库字段无法恢复已丢失的 stdio 管道。

## 8. 安全模型

### 8.1 配对和设备

- 配对链接是五分钟一次性高熵邀请；电脑显示设备名和验证码，由用户确认后才发放逐设备凭据；
- 电脑只保存凭据摘要，手机用 Android Keystore 保护的 AES-GCM 文件保存凭据；
- 每台设备可以单独撤销，撤销立即拒绝新请求并关闭活动 SSE；
- 长期凭据不放在 URL 查询参数；旧共享 Token 默认关闭，只在迁移期间显式开启；
- 设备共享主人权限，首版不引入复杂多用户 RBAC。

### 8.2 威胁边界

设备凭据等同于远程执行本机 Agent 的高权限密钥。网络入口、代理日志、截图、任务文本和 Agent 输出可能包含个人或项目机密。项目目录校验只约束 LeoAgent 文件 API，不限制 Agent 直接访问本机文件；需要更强隔离时另设容器或 OS 沙箱执行器。

## 9. 开源工程和支持矩阵

### 9.1 仓库职责

```text
android/   原生 Android 客户端
server/    Rust 服务、状态机、存储和 ACP 运行时
stt/       可选本地语音服务
deploy/    安装、配置和发行包脚本
docs/      API、架构、运维、发布和安全文档
tests/     受控 ACP、HTTP、安全和 Android 验证
```

首版保持单仓库、单电脑、单主人、多手机。只有当行为测试证明边界清楚后，才考虑多电脑档案、云推送、Relay 或插件市场。

### 9.2 支持矩阵

| 组合 | 开源首版口径 |
|---|---|
| macOS + Android + 已验证 ACP Agent | 首要支持目标 |
| Linux + Android | 代码可尝试；完成同等生命周期、路径和发行验收后再标记支持 |
| Windows + Android | 暂不承诺；需要独立的服务生命周期、截图和路径方案 |
| 其他 ACP Agent | 能力和版本逐项声明；“能启动”不等于“已验证” |
| iOS / Web 客户端 | API 预留，首版不并行开发 |

当前应公开区分“已有源码适配”“受控协议测试通过”“真实供应商实测通过”三个层次。已在 2026-10-20 以用户授权的临时项目完成一次 macOS + `@agentclientprotocol/codex-acp` 1.13.0（捆绑 Codex 0.155.1）最小任务实测；这只覆盖该平台和配置，不扩展为其他 Agent、平台或完整首版验收。最新证据以[实施记录](implementation-status.md)为准。

### 9.3 合并和发布门槛

每次变更至少验证受影响行为：

- Rust 格式、测试、clippy 和 all-features 构建；
- OpenAPI/事件 Schema 与真实 HTTP 响应；
- 断线、重复提交、并发审批、取消超时、服务重启和双实例；
- Android 构建、lint，以及凭据和回执恢复；
- 配置示例、文档链接、发行包校验和。

真实供应商 Agent 需要单独的隔离项目、明确版本、日期和人工授权；普通 CI 不保存个人模型凭据。发布物包括电脑端二进制、Android APK、SHA-256 和安装/回滚说明。正式 APK 必须核验包名、签名证书和版本身份。

### 9.4 对外协作和升级

延续仓库已有的 [Apache-2.0](../LICENSE)，维护 [NOTICE](../NOTICE)、[贡献说明](../CONTRIBUTING.md)、[安全报告入口](../SECURITY.md)和[变更记录](../CHANGELOG.md)。公开源码与发布稳定版本是两件事：源码可明确标为预览阶段，稳定性承诺必须跟随验收证据。

升级先做一致性备份，迁移失败停止提供服务；旧二进制不能假定兼容新数据库。回滚需要匹配版本的程序和备份、显式恢复及重新配对。安装脚本、平台版本、参考 Agent 版本、APK 签名身份及发布校验和写入发行说明，不以“编译成功”代替支持承诺。

## 10. 迭代顺序

### A：可发布的单电脑控制器

- 完成一个参考 ACP Agent 的一次隔离真实验收，并记录平台、版本、日期和限制；
- 固化 API v1、任务/交互/回执/unknown 语义；
- 完成配对、撤销、快照游标、重启对账和 Android 恢复；
- 完成手机响应丢失后进程重启、切网/锁屏和两台手机审批失效验证；
- 完成安装、doctor、backup/restore、CI 和发行包门槛。

按当前实现，契约验证、Android 故障注入和一次参考 Agent 实测已完成；下一阶段验证锁屏/切网、更多机型、安装/升级/回滚、远端 CI 和正式签名发行物。验收前不扩大 Agent 数量或引入云基础设施。

| 首版放行条件 | 可检查的证据 |
|---|---|
| 丢响应和重复提交 | 原操作 ID 只有一个任务、一次派发；参数冲突明确拒绝 |
| 手机断线/重启 | 从快照和原回执恢复，电脑任务不因手机离线中止 |
| 服务崩溃/取消超时 | 状态有解释，无证据进入 unknown，旧交互失效且不自动重发 |
| 多手机和撤销 | 一个审批只有一个有效决定；撤销关闭活动流并拒绝新控制 |
| 可自行部署和升级 | 干净环境安装、配对、最小任务、升级、备份恢复的记录 |
| 可公开分发 | 远端 CI、参考 Agent 版本记录、签名 APK 和发行物校验和 |

### B：多设备和恢复体验

- 扩展锁屏、切网和多设备的机型/系统覆盖，持续完善 A 阶段故障矩阵；
- 完善设备管理、审计导出、历史投影和恢复引导；
- 允许多个电脑连接档案，但每台电脑的项目、会话、游标和通知完全隔离。

### C：平台和适配器

- 先完善 macOS；再以同一行为测试验证 Linux；
- 在服务生命周期和文件/截图方案明确前，不列 Windows 支持；
- 将 Agent 注册表逐步配置化，保留能力声明和版本兼容检查。

### 暂缓

项目 Relay、云数据库、系统推送网关、端到端加密、多主机调度、Electron/桌面 IDE 和远程唤醒。这些功能会增加运维、威胁模型或平台承诺，应以独立设计进入，而不是让首版核心依赖它们。

## 11. Orca 的借鉴范围

参考 Orca 固定提交 `54f1417af7f0d710e8691dd19aba2648f675a274`，借鉴的是可靠性思想，不复制代码或其更重的云端拓扑：

| Orca 思路 | LeoAgent 的落地 |
|---|---|
| 操作账本、参数指纹和原子执行权 | SQLite 中的 `operation_receipts`、任务互斥和事务提交 |
| 会话身份与运行进程身份分离 | `session` 与 `runtime_instance` 分开，启动时按证据对账 |
| 重启恢复和 unknown | 派发边界、`recovering`/`unknown`、人工 resolve，不自动重发 |
| 快照加游标追赶 | 一致快照、SSE、HTTP 补取和 reset |
| 更重的 Relay、多宿主租约、工作区编排 | 首版省略，单电脑文件锁和项目互斥已经足够 |

借鉴的判断标准是：某项机制能否让手机断线、请求重试或服务重启后的状态更可解释；不能因为同类项目存在就把云服务、桌面同步或多主机调度加入核心。

依据为该固定提交的[操作账本](https://github.com/stablyai/orca/blob/54f1417af7f0d710e8691dd19aba2648f675a274/src/shared/agent-session-operation-ledger.ts)与[重启对账](https://github.com/stablyai/orca/blob/54f1417af7f0d710e8691dd19aba2648f675a274/src/main/runtime/agent-session-restart-reconciliation.ts)。本次重读了这两个实现，不把结论扩大为 Orca 最新版本的全面评估。

## 12. 设计评审问题

每项新增功能在合并前回答：

1. 电脑重启后，状态是否仍能解释？
2. 手机重试是否会再次触发副作用？
3. 用户能否区分已接受、运行中、结果未知和已中断？
4. 失败时能否通过原操作 ID 和事件游标恢复？
5. 是否引入新的云服务、凭据或平台承诺？
6. 当前支持矩阵和文档是否真实反映了验证证据？

如果无法回答，先补状态模型、错误传播和测试，再扩展 UI 或基础设施。
